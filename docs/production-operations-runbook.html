Ponyo Production Operations Runbook

A practical guide to admin access, safe releases, and post-deployment checks.

Verified: 27 November 2026 Production: Lightsail Tokyo · Docker Compose Audience: authorized Ponyo operators
Production is live. The storefront and API passed HTTP 200 smoke checks. Supabase Tokyo hosts the production database. Releases are manual; payment processing and scheduled-backup/restore readiness remain unverified.

Operating guardrails

Protect credentials and customer data. Never put passwords, tokens, private keys, `.env.prod` contents, or customer data in this document, chat, or shared command output. Keep this runbook only in an access-controlled repository or Drive folder.

Production runs on Lightsail instance ponyo-prod-tokyo at 13.112.48.83. The root domain and its admin, suppliers, and api subdomains point to this address. www.byponyo.com redirects to https://byponyo.com/. Caddy serves HTTPS.

Before the next release, confirm the repository's Caddyfile contains the same www redirect already applied on the server, so a later deployment does not lose it.

1Creating an admin account

First admin

Public registration cannot create an admin. If no admin can sign in, bootstrap the first account from an SSH session on Lightsail. The command prompts for a hidden password; it does not place the password in the command arguments or `.env.prod`.

Replace the email and first name with the authorized person's details. The example uses Ponyo's operations account:

cd ~/ponyo
sudo docker compose --env-file backend/.env.prod -f docker-compose.prod.yml run --rm --no-deps \
  -e INITIAL_ADMIN_EMAIL="hello@byponyo.com" \
  -e INITIAL_ADMIN_FIRST_NAME="admin" \
  api python -c 'import asyncio, getpass, os; os.environ["INITIAL_ADMIN_PASSWORD"] = getpass.getpass("Set admin password (hidden input): "); from app.seed import seed_initial_admin; created = asyncio.run(seed_initial_admin()); print("Admin created." if created else "An admin with this email already exists; password unchanged.")'

Password requirements: 8–128 characters, including at least one number and one symbol. Enter it only when the hidden getpass prompt appears. Never send or record the password.

  • If the command reports Admin created, sign in at admin.byponyo.com/admin-portal.
  • If the email already exists, the seed does not change that account's password. Do not rerun it expecting a reset.
  • If the email belongs to a non-admin account, the seed stops with an error. Do not change roles with SQL; have the operations owner verify the identity and account.
  • If the account exists, its password is unknown, and no other admin is available, stop and use an owner-approved account-recovery process. Do not reset the database or edit password hashes manually.

Additional admins

  1. Sign in and open Admin accounts in the Admin Portal.
  2. Enter the new admin's name, email, and temporary password.
  3. Share the temporary password through an approved private channel, not a group chat. Ask the recipient to change it after signing in if password changes are available.
  4. Remove admin access when it is no longer needed. The portal protects the current account and the last admin to reduce lockout risk.

Grant access only to authorized people. Customer and supplier accounts cannot sign in as admins.

2Releasing code changes

Before a release

  1. Make the change locally, run relevant tests, and request review under the team's process.
  2. After approval, commit and push to GitHub branch main. A push alone does not change production.
  3. Review database migrations, configuration changes, and DNS/provider changes separately.
  4. SSH to Lightsail and inspect the server repository before pulling:
cd ~/ponyo
git status --short --branch

If there are local changes, understand them before pulling or overwriting anything. This is especially important for Caddyfile: the www redirect was applied directly on the server and must also be retained in the repository.

Routine release without a database migration

Only after the server branch is clean and the approved changes are available on GitHub main:

git pull --ff-only origin main
sudo docker compose --env-file backend/.env.prod -f docker-compose.prod.yml up -d --build
sudo docker compose --env-file backend/.env.prod -f docker-compose.prod.yml ps
Never use docker compose down -v, delete volumes, or run git reset --hard as deployment steps.

Release includes an Alembic migration

Do not use the routine release steps by themselves. Before migrating:

  1. Review the migration and its impact on production data.
  2. Confirm a recent database backup is validated and recovery is approved.
  3. Schedule the release window and confirm the current Alembic revision and available heads.
  4. Build the API image with the migration, then run the migration only after approval:
sudo docker compose --env-file backend/.env.prod -f docker-compose.prod.yml run --rm --no-deps --build api alembic upgrade head

If a migration fails, do not rerun it, edit its revision, or restore a backup spontaneously. Preserve a redacted error and contact the operations owner.

Caddyfile-only change

The server file is mounted into the Caddy container. Validate before reloading:

sudo docker compose --env-file backend/.env.prod -f docker-compose.prod.yml exec caddy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
sudo docker compose --env-file backend/.env.prod -f docker-compose.prod.yml exec caddy caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile

Do not reload if validation fails. A code release does not require changing nameservers or email records.

3Post-release checks

Check service health and public endpoints:

sudo docker compose --env-file backend/.env.prod -f docker-compose.prod.yml ps
curl -sS -o /dev/null -w 'Site HTTP %{http_code}\n' https://byponyo.com/
curl -sS -o /dev/null -w 'API HTTP %{http_code}\n' https://api.byponyo.com/v1/health
curl -sS -o /dev/null -w 'WWW HTTP %{http_code} -> %{redirect_url}\n' https://www.byponyo.com/
Expected: relevant containers show healthy; site and API return HTTP 200; www returns HTTP 301 to https://byponyo.com/.

Then run browser smoke checks for:

  • Homepage and product detail page.
  • Admin sign-in and dashboard access.
  • Supplier sign-in using an approved test account.
  • Reservation/interest flow without completing a payment.
  • Verification or password-reset email only if production SMTP delivery has been confirmed.

Review logs if a check fails. Share only redacted excerpts:

sudo docker compose --env-file backend/.env.prod -f docker-compose.prod.yml logs --tail=80 api frontend caddy

Never share `.env.prod`, passwords, session tokens, customer addresses, or raw logs in chat or public tickets. Record the released commit, check results, and non-sensitive errors.

If a check fails, stop further changes. Do not rerun migrations, delete volumes, or attempt a restore until the backup and impact are confirmed.

Open operational items

  • Backups: confirm the owner, schedule, and location of automatic Supabase Tokyo backups. Run an isolated restore drill and record its date, duration, and result. Until then, recovery is unverified.
  • Staging and releases: there is no permanent staging environment or automatic deployment. Consider establishing staging and an approval/rollback procedure before routine releases.
  • Payments: keep Stripe disabled until credentials, webhooks, refunds, reconciliation, tax/shipping, and business approval have been tested.
  • Email and user journeys: verify production email delivery and customer/admin/supplier flows on the live domains. A healthy HTTP status does not prove every business flow is ready.
  • Blueprint: update vendor costs, access owners, renewal dates, backup/restore policy, and release approvers in the site blueprint.

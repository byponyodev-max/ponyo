Ponyo · System architecture

Application Architecture and User Flows

System overview, data connections, deployment, and user workflows. White-and-blue diagrams can be downloaded individually as PNGs for Google Docs.

System status: This describes implemented code and clearly marks disabled or unconfigured features. Local Docker Compose is the verified runtime; AWS production hosting is not deployed.

Figure 1.Overall application architecture

Main data path: portal → identity-scoped API route → FastAPI business logic → database / storage / configured provider → API response to portal.

Solid arrow: active request / data flowDashed arrow: optional or configuration-dependent service

Figure 2.Product discovery and catalog display

Only published products are returned by the public catalog endpoints.

Figure 3.Newsletter subscription and contact request

Contact requests are committed before SMTP is attempted, so notification failure does not discard the request.

Figure 4.Maker application, onboarding, and approval

Maker acceptance, onboarding approval, supplier activation, and product approval are separate steps. Application photos are stored privately.

Figure 5.Supplier product submission, admin review, and publication

New supplier products start unpublished and with checkout disabled. Admin publication requires Japanese and Korean translations.

Figure 6.Customer reservation or product-interest registration

Reservation and interest are distinct non-payment flows; the selected path depends on the product's shipping confirmation and reservation settings.

Figure 7.Conditional Stripe payment flow (not currently enabled)

When enabled, admin-only payment capture, void, refund, and sync use a durable transaction ledger; signed webhooks reconcile provider state. Product reservations and interests do not initiate Stripe.

Figure 8.Portal identities, sign-in, and authorization boundaries

These are three separate portal identities, not three separate databases or backend deployments. The supplier hostname rewrite is code-supported; public DNS and HTTPS for the subdomain are not established by this repository.

Figure 9.Customer account, cart, wishlist, and engagement features

The diagram separates code-supported APIs from features currently visible and enabled in the storefront.

Figure 10.Supplier offer and inventory change approval

The supplier can suggest changes but cannot change the public catalog directly. Admin approval applies pricing and capacity updates.

Figure 11.Paid order routing to supplier purchase orders (conditional)

This fulfillment routing is a post-payment commerce workflow. It is not triggered by non-binding product reservations or by reaching a reservation target.

Figure 12.Admin shipment management and customer delivery confirmation

Shipment records support partial fulfillment. Supplier confirmation does not mean that a parcel has shipped.

Figure 13.Admin Portal control plane and use cases

The Admin Portal is an operational control plane. It does not expose admin functions to the public storefront or supplier identity.

Figure 14.Email notifications, background processing, and localization

Database records are the source of truth; email and integration workers are conditional services, not evidence that production delivery is active.

Figure 15.Deployment: verified local runtime and planned AWS target

The current application runs locally; the AWS diagram is a target architecture, not a claim of production deployment. The API infrastructure plan does not define where the Next.js storefront will be hosted.

Source: repository implementation and project documentation. Local preview and temporary tunnel are not production deployment. Stripe checkout and newsletter campaign delivery are not active.

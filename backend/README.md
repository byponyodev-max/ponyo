# Ponyo API

FastAPI service for the Ponyo storefront. It is intentionally in the same repository as the Next.js app, but can be built and deployed independently.

## Local run

1. Copy `.env.example` to `.env.local` and set a random local `JWT_SECRET`. Keep all real secrets out of Git and out of `NEXT_PUBLIC_*` variables.
2. Start the local stack with Docker Compose (PostgreSQL, Redis, LibreTranslate, and API). The API applies Alembic migrations and seeds a small development catalog at startup. LibreTranslate loads English, Japanese, and Korean models on first startup; allow time for those models to initialize.
3. Set the frontend's `NEXT_PUBLIC_PONYO_API_BASE_URL` to `http://localhost:8000`, then run the frontend from the repository root.

Interactive API docs are available at `http://localhost:8000/docs` in local development.

Seeded demo products support two separate non-payment flows: reservations for destinations confirmed as shippable, and interest registrations for unsupported or unconfirmed destinations. Admins set each product's reservation status and target independently and configure confirmed shipping destinations; a null destination list means shipping has not been confirmed, while an empty list means confirmed unavailable everywhere. Checkout and reservation submissions block products whose destination is unknown or excludes the customer's country, but the catalog keeps those products visible and prioritizes deliverable items. Interest registrations are stored separately from reservations, accept supported country codes or a free-text country/region, and are reported separately by product and country in Admin. When a product's reservation target is reached, the API records the timestamp, creates a `product.reservation_minimum_reached` outbox event, and shows the status in the Admin Reservations report. This is an internal signal for the team to review production; it does not place a maker order automatically. Neither flow takes payment.

Shipping checkout and admin destination controls currently support Japan (`JP`) and South Korea (`KR`) only. Interest submissions remain available for other country/region values so the team can measure unserved demand.

### Phase 0 product and admin workflow

The admin portal at `/admin-portal` operates on catalog records already in the database. Admins can review and publish/unpublish products, set shipping proof, and manage reservation settings, but there is not yet a create-product intake form or supplier-to-admin product approval queue. Supplier catalog access updates offers and inventory for existing approved listings; it does not submit new product records. Maker applications are tracked separately and changing their status does not create a product. New products therefore still need to be added through the development seed or an authorized data/import workflow, then reviewed in Admin; publishing also requires Japanese and Korean translations. Do not treat the supplier portal or a maker application as a product intake path.

The backend uses LibreTranslate for Japanese (`ja`) and Korean (`ko`) translations. In Compose, it is available only on the internal network; direct backend development defaults to `http://localhost:5000`. Set `LIBRETRANSLATE_URL` and, if required by the server, `LIBRETRANSLATE_API_KEY` in the backend environment. Set `TRANSLATION_PROVIDER=disabled` to turn off uncached translations. The development seed writes reviewed Japanese and Korean cache rows for all 20 demo products into `product_translations`; rerunning the seed refreshes those rows without changing the table schema. Real products are translated and cached before admin publication. Product requests return `503` if a required translation cannot be generated; they do not silently substitute English.

### Contact notification email configuration

The API reads **backend** `.env`, then **backend** `.env.local` (local values win), using absolute paths relative to its application code, regardless of the launch directory. Process environment variables override both files. The repository-root/frontend `.env.local` is not a backend configuration source; never put SMTP secrets in `NEXT_PUBLIC_*` variables. An explicit `Settings(_env_file=None)` disables file loading for isolated tests. Containers can continue supplying environment variables without these files.

Contact mail routes general inquiries to `CONTACT_NOTIFICATION_EMAIL`, customer/order/delivery/plush requests to `SUPPORT_NOTIFICATION_EMAIL`, and maker/supplier/partnership inquiries to `PARTNERS_NOTIFICATION_EMAIL`. Maker applications are saved before a notification is sent to the partners inbox. Configure these with the SMTP transport variables `SMTP_HOST`, `SMTP_PORT` (587 for STARTTLS), `SMTP_FROM_EMAIL` (falls back to `SMTP_USERNAME`), `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_STARTTLS` (default true), and `SMTP_TIMEOUT_SECONDS`. If `SMTP_USERNAME` is set, its mailbox password is required. No alternate `EMAIL_*` or `MAIL_*` aliases are supported. Restart the backend after changing these values: settings are cached when the process imports the application, not reloaded per request.

`POST /v1/contact/requests` commits the contact record and `contact.request_received` outbox event **before** attempting SMTP. `emailNotificationSent=true` means SMTP accepted the message, not that it arrived in the inbox. False leaves the request saved; skipped transports log `reason=transport_not_configured`, and failures log only exception type and numeric SMTP status code (not provider response text, credentials, addresses, or message bodies). The contact outbox is an event-publication record, **not** a contact email retry queue: a pending event does not establish SMTP failure, and the order email worker does not resend these contact messages. Avoid resubmitting real customer requests merely to test email.

### Admin email inbox

The admin portal combines saved storefront contact requests and maker applications with messages fetched from the `hello`, `support`, and `partners` mailboxes over IMAP. Configure the per-address `EMAIL_INBOX_MAILBOXES__HELLO__*`, `EMAIL_INBOX_MAILBOXES__SUPPORT__*`, and `EMAIL_INBOX_MAILBOXES__PARTNERS__*` values in `backend/.env.local`. Each account uses the same mailbox username/password for IMAP and SMTP; the reply sender is selected from the mailbox the message arrived in (or the matching address for saved storefront requests). Hostinger's standard settings are `imap.hostinger.com:993` with SSL and `smtp.hostinger.com:587` with STARTTLS; confirm these in the domain's Hostinger hPanel if the mailboxes use a different provider or custom server settings. Passwords belong only in `backend/.env.local` or a secret manager, never in the frontend or source control. The sync worker polls every `EMAIL_INBOX_SYNC_INTERVAL_SECONDS` (default 60) and imports up to `EMAIL_INBOX_INITIAL_SYNC_LIMIT` messages per mailbox on each poll (default 500). Admins can also start a manual sync in the portal. The legacy `EMAIL_INBOX_IMAP_*` settings remain supported for a single mailbox.

Replies are queued through the existing durable SMTP notification worker, use the configured `SMTP_FROM_EMAIL`/`SMTP_USERNAME`, and carry `In-Reply-To` and `References` headers when available. The portal displays queued, sending, sent, and failed states; a queued response means it is pending delivery, not that the recipient received it. Configure SMTP as described above before enabling replies. Run migration `20261120_0030` before deploying this inbox code; the migration creates the inbox messages and IMAP cursor tables.

For diagnosis, compare only variable names/presence and masked equality between the process and backend files, and inspect contact/outbox counts, statuses, and timestamps without payloads. A single clearly labelled diagnostic to the configured admin can establish SMTP acceptance. For missing inbox delivery after acceptance, inspect spam, filtering rules, provider delivery/bounce logs, and SPF/DKIM/DMARC. SMTP acceptance alone cannot establish or repair downstream mailbox delivery. Historical contact records do not store the SMTP result, so their delivery outcome cannot be reconstructed from their status alone.

## Direct Python development

Use Python 3.12+ and install the project with its `test` extra. Start PostgreSQL and Redis first, then run `alembic upgrade head`, `python -m app.seed`, and `uvicorn app.main:app --reload` from this directory.

The full Alembic chain targets PostgreSQL. SQLite can run local previews/tests against a model-created schema, but migration `20261109_0006` uses PostgreSQL-specific SQL and cannot bootstrap a fresh SQLite database. Do not treat SQLite test success as PostgreSQL migration certification.

CI runs the API tests with SQLite and separately generates the full migration SQL with an explicit PostgreSQL `DATABASE_URL`. The `alembic upgrade head --sql` step is offline: it needs the correct dialect but no running PostgreSQL server or real database credentials. This checks SQL generation, not execution against PostgreSQL; staging must still run online migrations before release.

For an existing populated database without an Alembic version record, **do not run upgrade or stamp blindly**. Back up first, compare tables, columns, types, indexes, constraints and defaults against the migration target, then reconcile the baseline deliberately. The local preview database has no recorded Alembic revision; its populated schema must be checked before applying individual additive revisions. `GET /v1/health` checks connectivity with `SELECT 1`; it does not certify schema/migration readiness.

## Routes

Storefront database entities, supplier demo fixtures, relationships and rollout limits are documented in [storefront database](../docs/storefront-database.md). Revision `20261111_0015` adds normalized categories, brands, galleries, suppliers/offers/inventory, account carts and order status history. Run migrations before updated application code. The local unversioned preview baseline still requires deliberate reconciliation; do not blindly upgrade/stamp it.

- `GET /v1/health`, catalog, product detail
- CSRF token, register, login, current account/profile updates, saved addresses, and persistent customer wishlist
- Pending registration, 24-hour single-use email verification, and resend recovery; account sessions are issued only after verification
- Product ratings/reviews and durable per-product coming-soon waitlists
- One-hour, single-use password reset requests and confirmation (`SMTP_HOST`, `SMTP_FROM_EMAIL`, and SMTP credentials must be configured for delivery)
- SMTP STARTTLS transactional email for verification/reset plus durable order, payment, shipping, delivery, cancellation and successful-refund notifications with retry tracking; see [operations reliability](../docs/operations-reliability.md)
- Database-backed customer/supplier/admin roles with explicit role guards; public registration cannot assign elevated roles. The `/admin-portal` UI and `/v1/admin/*` APIs require an admin session.
- Admin account list/create endpoints (`GET/POST /v1/admin/admins`); account creation is admin-only, CSRF-protected, stores a password hash, and provisions the account as email-verified
- Admin email center with IMAP inbox sync, storefront contact/maker messages, threaded SMTP replies, and reply templates; requires migration `20261120_0030` and mailbox/SMTP configuration
- Product-scoped reservation and separate interest reports, filtered reservation details, and CSV/XLSX exports (`/v1/admin/reservations/export.csv` and `/v1/admin/reservations/export.xlsx`)
- Revocable session versions: logout revokes all current account sessions; password reset atomically consumes its token and invalidates existing sessions
- Authenticated order history and detail
- Authenticated persisted carts (`GET/PUT /v1/cart`); guest browser carts remain local
- Public read-only `POST /v1/cart/validate` refreshes source prices/supplier availability and flags unavailable or changed-price lines without removing them
- Multi-supplier carts and checkout use per-line supplier offers, transactional stock revalidation, and optional price expectations; cart/checkout limits are 100 unique variants and 99 units per line
- Verified-account checkout with server-priced variants, customer-scoped request idempotency and Stripe-hosted payment; guest checkout is not accepted
- Server-authoritative checkout quotes, configurable shipping/tax, capped percentage/fixed coupons, immutable item snapshots, customer cancellation and admin fulfillment transitions; see [checkout and order management](../docs/checkout-order-management.md)
- Linked supplier-stock reservation/settlement and transactional order status history (demo supply only until real onboarding)
- Provider-confirmed reservation-expiry recovery worker and trusted stock snapshot synchronization; timestamps distinguish inventory mutations from the last supplier observation
- Newsletter/contact submissions
- Stripe signature-verified webhook endpoint with an idempotent transactional outbox publisher to SQS
- Stripe authorization/capture, protected refunds, payment synchronization and durable transaction records: [payment gateway](../docs/payment-gateway.md). Payment deployment additionally requires migration `20261111_0020`.
- Supplier-scoped purchase orders, order splitting, forwarding/confirmation, alternative routing and durable retry protection: [supplier order management](../docs/supplier-order-management.md). Requires migration `20261111_0021`; outbound forwarding defaults off until a real idempotent supplier adapter is configured.
- Separate supplier fulfillment and multi-shipment tracking, partial line quantities, HTTPS tracking links, status events and customer delivery confirmation: [shipment management](../docs/shipment-management.md). Requires migration `20261111_0022`; carrier statuses are operator-entered until a signed provider integration is configured.
- Aurora point-in-time backups, CloudWatch API/database/DLQ/email alarms and restore-drill guidance: [operations reliability](../docs/operations-reliability.md). Terraform changes require review and apply; no infrastructure deployment was run.

## Production deployment notes

### Testing verification before deployment

Deployment is not required when opening the email on the same computer that runs both local servers. Keep frontend/API running and open the email button in that computer's browser. A `localhost` link opened on a phone points to the phone, not the development computer.

For cross-device tests, use a reviewed HTTPS development tunnel or staging environment for **both** frontend and API. Set `STOREFRONT_BASE_URL` to the frontend's public HTTPS origin, add that exact origin to `FRONTEND_ORIGINS`, and set the frontend's `NEXT_PUBLIC_PONYO_API_BASE_URL` to the public API origin. Restart both servers and resend the email; older messages keep their original URL. Never expose a development API or database publicly without reviewing access controls. Different-site tunnel hostnames can block cookies; use same-site hostnames or staging with the intended cookie domain for reliable auth testing.

Verification mail includes an HTML button. With a public HTTPS storefront, Ponyo email uses the official logo at `/profile.png`, allowing Gmail's image proxy to retrieve it. Local HTTP development uses an inline CID PNG with explicit MIME root metadata. Email apps may still hide images until the recipient permits them. A plain-text alternative keeps the secure URL accessible to text-only email clients. The button points to the same single-use verification page; styling does not change activation or token security. Gmail on mobile cannot reach a computer's localhost and may sanitize local links; use a public HTTPS URL and resend after changing it.

For a single-origin development tunnel, opt in to `PONYO_DEV_API_PROXY=true` and set `NEXT_PUBLIC_PONYO_API_BASE_URL=/ponyo-api` for the frontend process. The development-only rewrite forwards `/ponyo-api/v1/*` to the loopback API at port 8000, not the database or API docs. Set `PONYO_DEV_TUNNEL_ORIGIN` to the exact temporary HTTPS frontend origin to permit development assets. The backend process must use that origin for `STOREFRONT_BASE_URL` and include it in `FRONTEND_ORIGINS`. These temporary process overrides are not production configuration, stop working when the tunnel stops, and must be updated for each new quick-tunnel URL. Stop the tunnel after testing; do not share the URL publicly.

Apply Alembic migrations through `20261120_0030` before deploying the current application. Revision 0030 adds the admin email inbox and IMAP sync cursor; revision 0029 adds a separate product-interest table; 0028 adds nullable per-product shipping destinations; revision 0027 records when a product reaches its reservation target. Revision 0026 extends the product translation cache to storefront fields such as category/type, materials, dimensions, dispatch text, image alt text, variant labels/options, and maker descriptions. Revision 0025 adds maker profiles and reservation records; revision 0024 removes product price history. Revision 0023 adds durable email retries and checkout idempotency; revision 0022 adds separate supplier fulfillment status and shipment/event records; revision 0021 adds supplier purchase orders, and revision 0020 adds payment transaction records. Revision 0019 adds order totals, item snapshots and coupon rules; revision 0018 adds the app translation cache. Revision 0017 adds nullable expiry/sync timestamps without changing stock. Revision 0016 adds trusted account roles and nonnegative session versions; existing accounts default to customer/version zero without changing credentials or verification state. Revision 0014 requires existing unverified accounts to use resend/verification before signing in. The schema represents pending status with `email_verified=false`; there is no separate activation status that can drift out of sync. See the [authentication contract](../docs/backend-api-contract.md#customer-authentication-and-access-control) for logout scope, reset delivery privacy, and role limitations.

Configure `STOREFRONT_BASE_URL` as the public HTTPS storefront origin (also present in `FRONTEND_ORIGINS`) and configure `SMTP_HOST`, `SMTP_FROM_EMAIL` (or `SMTP_USERNAME`), and SMTP credentials. Production startup rejects missing email transport or an invalid storefront origin. Without local SMTP, verification links are logged for development, but the API reports delivery failure rather than claiming mail was sent. Verification delivery is synchronous: failure returns `503`, preserves the pending account, and lets the customer retry through resend. There is no automatic delivery retry worker for verification mail.

Before declaring email E2E complete, use a controlled real mailbox on staging: register, confirm the account remains pending and login/checkout are blocked, inspect inbox/spam, open the received public-domain link, sign in, and start Stripe test checkout. Repeat resend, expired/reused links, and SMTP failure/recovery. Check provider delivery/bounce logs and SPF/DKIM/DMARC. SMTP acceptance and mocked transport tests do not establish inbox delivery. Never include verification tokens or SMTP credentials in tickets or screenshots.

Deploy the container to ECS/Fargate in `ap-northeast-1` behind an HTTPS load balancer. Use task IAM roles, Secrets Manager, private Aurora PostgreSQL and Redis subnets, exact CORS origins, shared-domain Secure cookies, TLS, WAF/rate limits, and CloudWatch. Configure Stripe webhook delivery to `/v1/webhooks/stripe`. The API publisher sends durable outbox events to SQS; a separate idempotent consumer must still process fulfillment and notifications before connecting real supplier systems.

This repository contains a development catalog seed, not supplier-approved inventory. Replace it with verified catalog/stock feeds before accepting real payments. Production rollout also requires a real domain, AWS account, Stripe test/live configuration, email delivery provider, fulfillment consumer, monitoring/alerts, and privacy/retention policies. No deployment has been run from this workspace.
